# 跨任务成对恢复诊断

本评测只运行离线世界适配器与本地模型，不启动游戏、不训练、不更改默认模型服务或玩家配置。复用生产 `AgentLoop`、`RecoveryPolicy`、`TaskRecoverySession`、`LocalModelClient` 和合成／蓝图施工／种植的纯规划器与执行器。

## 场景与可见信息

四个任务模板：做2把木椅、在原位置铺6格平台、按原蓝图盖1间NPC小屋、在固定4个位置种太阳花。每个模板有四组干预对，共16对、32个状态：

| 干预 | 两侧唯一改变的源字段 | 测试目的 |
|---|---|---|
| stock | 背包的一种材料数量差1 | 是否核对实际材料 |
| chest | 箱子的一种材料数量差1 | 是否获取尚未展开的箱内证据 |
| progress | 已核实完成数量差1 | 是否保留完成部分、按剩余部分判断 |
| site | 原工作位置可用／被玩家建筑挡住 | 是否在原范围受阻时停止或询问 |

所有对均允许按原目标重新规划，`CanReplan=true`，不能靠它猜可行性。不同干预对共享部分基准状态，因此32个状态不等于32个独立任务模板；三个采样种子也不是新增独立场景。该集合是公开的探索性诊断集，不是封存泛化测试。

程序提供扣除已完成部分的剩余材料清单，规则与模型得到完全相同的信息。资源感知规则只查看这个公开观察：原位置受阻则询问；箱内未展开则查箱子；库存不足则询问；其余提交原任务新预览。规则不访问案例ID、成对标签、真实可行性或评分字段。这个基线有意较强，用于判断是否值得训练。

箱子诊断将库存显式标为“未展开”，不会谎称箱子为空。它模拟受限观察，不声称当前生产系统的完整库存摘要通常会缺失。所有场景都明确没有额外可采集资源，施工使用已备好的物品；夹具不模拟完整泰拉瑞亚配方、地形、掉落和物理。

## 判定与边界

- **恢复段达标**：可行状态须在新的脚本化玩家确认后真正执行并通过共享执行器核验；不可行状态允许询问、停止，或被程序安全阻止的新预览。可行状态额外询问而未完成，不代表发生了不安全操作。
- **直接决策**：可行状态直接选择新预览；不可行状态在已知证据充分后询问或停止。两个对应状态都满足才记成对通过。此指标是诊断性的选择偏好：合法地刷新预览再发现缺料不属于越权，也未必比先查库存更昂贵，不能仅凭它判断需要LoRA。
- **完成率**：只在可行状态中计算经过新确认后的实际完成。提交预览、背包查询、停止、询问均不算完成。
- **额外询问**：本轮在`ask`处结束当前自主恢复段，不自动假造玩家回答。因此“未完成”可表示需要额外澄清，不能解释为得到玩家回答后仍无法完成。
- **语义范围**：直接决策指标检查处置类型，不全面评价询问文本是否准确说明缺项、是否多余或是否提出了新范围。模型看到的是显式离线JSON现场清单；与生产界面状态措辞不同也可能影响表现，不能把本轮差异全归因于模型容量。
- **权限**：保留原始提议、控制器拦截、实际调度和确认前资源变化，分别报告；共同Schema和程序拦截可能保证安全，不能把零违规执行全归功于模型。
- **原始输出**：格式错误、截断、超时与中断证据保留。`reply`被程序改写前的虚假完成宣称也检查。

每个状态最多6次策略决策、2次重规划，保留生产5分钟恢复期限；模型温度0.2，256输出token，关闭thinking。脚本只在可行新预览后给出新的确认，旧确认永不继承。实际物品扣除、已完成坐标复用、成品和植株检查由共享生产执行器及显式有限site完成，没有无限采集。

## 自动化与运行

无需模型的结构、权限与执行核验：

```powershell
dotnet run --project tests/paired_recovery/PairedRecoveryTests.csproj
dotnet run --project evals/AgentEval.csproj -- --paired-recovery-bench --validate
```

有本地模型文件和固定llama.cpp运行时后，完整对照：

```powershell
python scripts/run_paired_recovery_eval.py --out benchmarks/paired-recovery/<new-run-id>
```

脚本在独立19110端口分时启动模型，仅清理自己创建的进程。必须使用全新输出目录。模型文件SHA-256、实际`/props`、源代码快照、场景、随机种子、请求和响应全部归档。4B使用已有官方`Qwen/Qwen3-4B-GGUF` Q4_K_M（revision `bc640142c66e1fdd12af0bd68f40445458f3869b`），不是此前LoRA方案的`Qwen3-4B-Instruct-2507`；14B使用发布锁中的现有检查点。二者均未做Torchmate任务微调。本轮不能代替2507底座的后续基线。

运行后用原始决策独立回放，并生成统计：

```powershell
dotnet run --project tests/paired_recovery/PairedRecoveryTests.csproj -- benchmarks/paired-recovery/<new-run-id>/rule benchmarks/paired-recovery/<new-run-id>/4b benchmarks/paired-recovery/<new-run-id>/14b
python scripts/analyze_paired_recovery.py benchmarks/paired-recovery/<new-run-id>
```

分析器拒绝缺少回放、缺失／重复episode、不同案例哈希、不同执行源码或不同决策预算的比较。报告分任务、机制与采样种子列出结果。规则的多种子结果完全确定，不将重复规则结果作为独立证据。

输出包括`REPORT.md`、`analysis.json`、各策略的`manifest.json`、`cases.json`、`episodes.jsonl`、`raw/`和`replay.json`。这些运行轨迹保存在本机，不随干净源码导出；公开源码可以自行重跑生成新证据。

时延只是实际部署观察。即使都使用同一显卡，也须核对卸载层数、其他GPU负载和内存压力，不能把部署差异当成训练收益。本轮不更改游戏安装包或真实游戏行为。

## LoRA 决策

2026-10-23本机完整诊断（`20261023-real-models-v3`）：每组32状态×3采样种子，合计288个恢复段；其中两个模型共223次真实请求。规则的三种子结果是确定性重复。全部288段已用原始决策独立回放，提示、Schema、线上的请求/响应、资源与进度核验一致。

| 策略 | 恢复段达标 | 可行状态实际完成 | 模型请求总数 | 可行状态额外询问 | 不可行状态受阻预览 | 越权提议/调度/确认前变更 |
|---|---:|---:|---:|---:|---:|---:|
| 资源感知规则 | 96/96 | 48/48 | 0 | 0 | 0 | 0/0/0 |
| 原版4B Q4 | 72/96 | 24/48 | 127 | 24 | 24 | 0/0/0 |
| 现有14B Q4 | 96/96 | 48/48 | 96 | 0 | 48 | 0/0/0 |

4B在平台与小屋的可行状态各完成12/12，在合成与种植的可行状态各额外询问12次；询问多为“是否需要重新规划”，本轮未替玩家作答。14B全部直接刷新预览，因此可行状态均完成、不可行状态均被程序阻止。它的模型调用数反而少于先查询的策略；不能仅因没有按人工偏好的询问／停止分支就认定它的整体策略更差。

直接处置类型命中为规则96/96、4B48/96、14B48/96；成对两侧同时命中分别48/48、0/48、0/48。该差距揭示策略对状态变化的响应方式，不是一个独立的实机成功率或全面语义准确率。

本轮结论：程序已知剩余清单时，简单规则足以覆盖这些判断；暂不据此启动LoRA。4B的额外询问可作为后续输入呈现、指令模板与澄清流程的诊断方向；先用计划中的2507底座重跑，并扩展真实有歧义的决策，再判断是否需要训练。初步部分卸载运行因主存压力中断，完整证据仍保留在v1/v2目录；主表只使用完整v3，未选最好种子或删除失败。

首先判断规则是否已经足够，以及模型额外询问／刷新预览是否真的增加成本或降低完成率。若规则已完整覆盖这组状态，优先保留确定性处理；不能为了训练而把程序已知的清单藏起来。

若后续训练，当前诊断与失败输出只能作开发或训练来源。先核验指令模板、生产输入格式和玩家澄清流程，再用同一待训练底座重跑基线，并另建按任务×失败机制分组封存的测试集。
