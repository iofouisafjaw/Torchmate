# PAHF + SkillEvo：4B 同伴闭环设计

状态：0.4 已实现经历与测量、昼夜条件记忆、澄清恢复和反馈修改；SkillEvo、技能库与 LoRA 尚未接入。本文保留后续设计，当前能力与验证边界见下文和 [README](../README.md)。

0.6 在上述闭环上补充了单人对话暂停、无默认快捷键的面板、提示缓存和澄清循环修复。偏好理解不再读取世界钟表来限定规则，输出语法根据玩家原话限制合法时段；已知时段问题的简短回答可直接解析绑定的候选规则。原话保留为来源证据，不支持的护卫请求单独说明。以上是交互与可靠性改进，不是权重训练或技能演化。验证见 `tests/verification-v06.json`。

### 0.4 实现对应关系

- 继续使用现有 `key/value`，新增 `when=any|day|night`，没有引入完整技能 DSL；旧版偏好迁移为 `any`。操作规则修订号独立保存。
- 模型原始 `mode=act|ask` 与代码检查分开记录。提示提供完整条件规则和当前时段，不把代码算出的 allow/ask 答案交给模型。
- 规划器单独接收结构化 `rules` 和 `time`；操作规则不会因软性备注的字符预算而被截掉。输出先选 `action`，再选 `mode`，语法仅允许采集动作使用 ask。开发时曾出现“mode 先选 ask，随后被语法迫使选采集而无法说明缺工具”的退化，因此保留动作顺序和缺工具回归用例。
- `EpisodeRecorder` 串联经历、对话、任务、决策；反馈关联、动作前后快照、原始目标方块收据写入 JSONL v2。`memory.json` 保持 v1 的可兼容增量字段。
- 等待澄清时保留被中止的原任务；明确回答后按新状态重新规划。两分钟内的确认／澄清绑定当前世界会话、玩家或任务、昼夜及规则修订号；过期或情境变化取消等待。
- `scripts/report_learning.py` 只读报告请求量、延迟、主动／强制／多余询问及实际目标变化。token 用量、独立任务成功 oracle、物品掉落归因、全面树木连锁变化仍缺失，不能视为已测。
- `tests/LearningLoopTests.cs` 为开发用教学与回忆场景，不是独立晋升／最终测试集。A0 有对照样例；完整 A0/A1 消融、冻结晋升集和统计学习效果仍待后续实验。禁止把调试通过率作为 SkillEvo 改进证据。

### 0.4 本机开发验收

- 77 项核心检查、2 项报告测试通过；真实 Qwen 的 10 个回忆场景和 3 个动作回归场景通过。
- 私有无界面测试世界跑通教学、夜间等待、昼夜变化使旧确认失效、同意后采集、白天直接采集、反馈漂移、澄清及原任务重新规划。7 段经历全部闭合，3 次原始目标移除均有前后快照和直接收据。
- 5 次有效提议：必要询问由模型主动完成 3/3，代码补拦 0/3，多余询问 0/2。无效提议另计，不能从询问率的分母中忽略后再宣称整体成功。
- 本轮 16 个请求、13 个响应，另 3 个在任务结束时取消。Intel Mac CPU、4 线程、2048 上下文；响应中位约 22.8 秒，P95 约 43.8 秒。尚未测试游戏界面、物理、寻路和 FPS。

历史快照保存在本机 `tests/verification.json`，包含包哈希、源码摘要、原始回忆输出和游戏测量，不随源码导出。提示曾依据这些开发用例调整；这不是独立泛化评测，也不是权重训练或 SkillEvo 收益的证据。

## 1. 要回答的问题

固定 Qwen3-4B、短提示和有限推理次数，能否从少量日常纠正中获得有适用条件的合作规则，在新场景使用，并在偏好变更后及时调整？

本阶段的“学习”是外部记忆和合作策略的更新，模型权重保持不变。需要证明系统的后续选择发生了可归因的变化，不能用模型说“记住了”作为证据，也不能把代码拦截成功当成模型已理解。

采用两种方法的机制，不直接部署整套上游框架：

- [PAHF](https://arxiv.org/abs/2602.16173)：行动前澄清、行动时使用偏好、行动后用反馈更新记忆。[代码](https://github.com/facebookresearch/PAHF)
- [AutoSkill / SkillEvo](https://github.com/ECNU-ICALK/AutoSkill)：提炼可复用技能，再通过回放、修改、评估、版本晋升来改善；上游 SkillEvo 目前尚未自动写回主技能库。[实现说明](https://github.com/ECNU-ICALK/AutoSkill/blob/main/SkillEvo/README.md)

## 2. 首个实验只处理昼夜与采集

玩家教学：“以后夜里采集先问我，白天不用。”

期望行为：

1. 夜里收到采集任务，先提出具体目标并等待；玩家确认后只执行该动作。
2. 白天收到相同任务，直接执行允许的动作，不反复征求同意。
3. 换措辞、换目标坐标、换采集类型，仍按教学涵盖的条件判断。
4. “这次不用问”只对当前动作有效，不能改永久规则。
5. “我改主意了，以后白天也先问”立即修改当前规则，旧策略不能继续绕过它。
6. 重进当前世界继续有效；另一个世界使用自己的规则和技能。

选择昼夜是因为当前 `CompanionPrompt` 已有 `Main.dayTime`，可先研究闭环。下一阶段才加入玩家明确标注的家园区域；不能让模型猜测“家附近”的边界。

## 3. 两个相连但更新速度不同的循环

### 3.1 游玩中的即时循环：PAHF

玩家话语 → 绑定当前情境和相关任务 → 提取偏好或发起澄清 → 保存明确指令 → 检索当前规则与有效技能 → 模型提出动作及是否先问 → 代码检查 → 游戏执行 → 记录实际效果 → 绑定玩家反馈。

明确的“禁止／停止／改主意”即时生效，不等待离线评分。已明确的授权仍须通过工具、世界边界等既有检查。模型推断出的更宽权限不能由“回放分高”自动获得。

### 3.2 游玩之外的改善循环：SkillEvo

整理已闭合经历 → 提炼或修改合作技能候选 → 先在开发集回放 → 选出一个候选 → 独立晋升集检验 → 晋升或保留旧版 → 后续真实执行中继续观察，必要时停用、回滚。

初期手动触发演化；不在游玩期间争抢 CPU，也不假定退出游戏后 tModLoader 仍会继续工作。无独立评测样本时，候选保持待验证状态。

## 4. 三种数据分别管理

| 数据 | 内容与来源 | 更新与权限 |
|---|---|---|
| 明确规则 | 用户直接表达的条件、行为要求、原话、时间、规则版本 | 即时更新；代码执行其已支持的语义 |
| 经历 | 决策前状态、模型提议、拦截／确认、真实变化、反馈及其关联 | 追加保存；成功、失败、未知分开标记 |
| 合作技能 | 从经历中总结的条件化操作方法、证据、版本和验证结果 | 候选经回放检验后才能进入活跃库；不能改变用户授权 |

合作技能第一版是短文本／受限 JSON 操作说明，不生成 C#、不执行模型生成的脚本。允许修改提醒方式、检查顺序、任务相关的澄清策略；不能修改动作验证器、测试答案或权限检查。

拟议规则示例：

```json
{
  "id": "night-gather-confirmation",
  "selector": "gather",
  "when": { "time": "night" },
  "effect": "ask",
  "origin": "explicit_player",
  "sourceTurnId": "turn-17",
  "revision": 1
}
```

受限语义：`selector = gather | mine | chop`，`time = any | day | night`，`effect = allow | ask | deny`。解析不到受支持语义或条件不清时，询问玩家，不降格为无条件授权。

规则冲突：全局禁令继续生效；同一选择器和条件的新明确修改替代旧版；更具体的规则可以约束一般规则，不能自行覆盖更高层禁令；无法确定优先级时停止并询问。条件未知时不能擅自当作白天／野外。

`gather` 包含 `mine/chop` 是系统预先定义的动作分类。跨这两个动作的测试检验条件规则的正确应用，不宣称模型自行学出了新的游戏动作或动作分类。

拟议技能示例：“执行采集前检查当前昼夜与适用偏好；需要确认时提出具体目标；只有当前动作获准后才执行；每个新目标重新检查。”规则的具体值从当前规则库读取，不复制成永不过期的技能文本。

## 5. 当前代码具体要改什么

| 模块 | 当前情况 | 拟议修改 |
|---|---|---|
| `Content/Companion/PreferenceProtocol.cs` | 固定 key/value、长期表达检查 | 条件规则提取、受限 DSL、明确指令／临时许可／不确定／纠正的分类；不确定输出澄清问题 |
| `Content/Systems/CompanionDialogueSystem.cs` | 每条话先中止任务，提取后立即保存 | 中止前保存上下文与经历 ID；增加等待澄清状态，回答后恢复仍有效的原任务；把反馈绑定到正确经历 |
| `Content/Systems/ChatCoordinator.cs` | 普通对话、确认、反馈、记忆指令 | 区分“回答问题”和“确认动作”；增加技能查看、手动演化、回滚入口 |
| `Content/Companion/CompanionStore.cs` | 平面偏好、少量对话、JSONL | 规则版本、技能版本、证据索引、候选状态、原子晋升、回滚；旧数据迁移，保留世界隔离 |
| `Content/Companion/CompanionProtocol.cs` | 模型仅输出一个动作 | 在现有动作外增加简短 `mode=act|ask`，保留动作目标，让原始计划的询问意图可评估 |
| `Content/Systems/CompanionPrompt.cs` | 当前状态和有界记忆 | 同时给提取与规划传递类型一致的昼夜、工具、位置；最多检索少量当前有效技能和相关经历 |
| `Content/Companion/CompanionPolicy.cs` | 无条件采集确认／禁止 | 条件匹配、优先级、规则版本检查；独立于模型执行，不把计算出的测试答案回填给模型 |
| `Content/NPCs/AIAgentNPC.cs` | 规划、执行、等待具体动作确认 | 保留原始 mode；分别记录模型主动询问与代码强制询问；确认绑定情境和规则版本，变化时重新检查 |
| `Content/Actions/MineAction.cs`、`ChopAction.cs` | 返回执行状态与简短结果 | 生成真实效果收据：实际改变的方块、类型、目标及可归因的资源变化；避免“最后一格已空”被当作任务完成 |
| 新 `EpisodeRecorder.cs`、`SkillBank.cs` | 无 | 管理经历、反馈归属、技能状态与依赖规则 |
| 新离线 replay/evolution 工具 | 无 | 重用同一 C# 协议／规则评估实现，串行调用本地模型，保存候选比较报告 |
| `tests/` 与独立游戏诊断模组 | 协议、存储、单一挖矿闭环 | 增加学习前后、场景迁移、偏好漂移、消融与真实昼夜执行实验 |

拟议状态：`Idle → Understanding → WaitingForClarification / Planning → WaitingForApproval / Executing → Observing → Idle`。离线候选状态：`incubating → candidate → active → retired/rolled_back`。

澄清和动作确认各有独立 ID、世界会话、父任务、有效期；一条“同意”不能跨状态或跨任务复用。等待期间跨越昼夜边界、规则变更或换世界时，原确认必须失效或重新检查。

## 6. 补齐经历，才能学习和回放

每个经历至少记录：

- `episodeId / worldId / sessionId / turnId / taskId / decisionId`，以及实际使用的规则和技能版本。
- 决策前快照：昼夜、目标、工具、背包有关物品的完整计数；不能只保留任意前六个物品。
- 模型原始提议：mode、动作、坐标；匹配的记忆 ID、代码放行／拦截原因，以及确认事件。
- 执行效果：动作前后目标方块变化；能直接归因于本次动作的效果；无法归因的变化标为未知。
- 玩家反馈原话、反馈针对哪个任务、纠正后的目标行为、来源和时间。

没有反馈不等于玩家满意；玩家说“谢谢”不等于目标完成。寻路失败、工具不足和偏好误判分别标记，避免把执行器缺陷学成玩家偏好。

一般闲聊保留近期上下文即可，不要求每句话触发一次演化。涉及“刚才那次”的纠正只有在关联明确时才自动绑定；多个可能任务时先澄清。

## 7. 即时规则与技能晋升的衔接

明确规则保存后，相关旧技能先检查兼容性：若包含已过期的规则值，停用或回退到通用策略。即使新技能未验证完成，也不能继续执行旧权限。

技能必须记录依赖的规则 ID／版本、证据经历和来源。晋升时复核世界、规则修订号和候选父版本；离线评测期间玩家又改了偏好，则本次候选过期，不能覆盖新规则。实际禁令始终由当前规则库裁决。

新偏好改变了正确答案时，按新的偏好版本生成测试视图；只保留仍有效的旧要求做回归。不能要求新候选同时满足两条互相矛盾的历史偏好。

所有数据继续按世界 UUID 保存；规则、技能、回放集、候选和验证报告都不能跨世界默认共享。忘记规则时，要使其派生技能和相关检索索引失效，不能只删除一条显示文本。

## 8. 如何证明“确实学会了”

### 8.1 分开记三种成绩

1. **记忆成绩**：是否正确提取、替换、取回相关规则。
2. **规划成绩**：代码干预前，模型选择的 mode、动作和目标是否符合当前偏好。
3. **执行成绩**：最终实际发生的游戏变化是否符合规则、是否完成任务。

模型想夜间直接挖矿、被代码拦住：执行约束合格，规划仍记错，不能算“模型学会”。一直拒绝、一直询问或一直闲聊也不能凭零破坏拿高分；必须同时衡量白天的有效完成和不必要询问。

### 8.2 固定基线与消融

| 组别 | 能读取什么 | 回答的问题 |
|---|---|---|
| A0：不积累偏好 | 相同当前状态、相同通用提示与执行保护 | 没有学习时表现如何 |
| A1：当前 0.3 思路 | 相同教学与反馈、平面偏好检索，无技能演化 | 条件化闭环相对现状是否有用 |
| A2：PAHF 条件规则 | 条件记忆、行动前澄清、行动后纠正，无技能演化 | 改善是否来自更好的记忆与反馈，而非演化 |
| A3：完整提案 | 与 A2 相同，再加经过回放晋升的技能 | SkillEvo 额外带来多少提升 |

评估规划时，各组看同一批状态和指令；执行保护一致，不向基线暴露隐藏的玩家偏好答案。教学数据、模型文件、量化、解码设置、提示上限和允许的请求次数记录在报告中。询问得到的新信息也要计入交互成本，不能视为免费。

为避免保护代码掩盖组间差异，规划消融使用同一份已经核实的授权规则作为外层执行保护，但不向模型暴露它计算出的当前裁决；模型可见的记忆／技能按组别变化。这样最终零误执行只能说明保护有效，学习收益主要看干预前规划和询问成本。另行测试“原话 → 各组保存的规则”的正确性，防止一份人工修正的规则库掩盖提取错误。隐藏的评测标签仅供评分，不能送入生产执行器或候选生成器。

教学结束后清空近期聊天，只保留该组允许的长期记忆／技能。用关闭学得技能、恢复旧版本等消融检查行为变化是否来自新增状态，而非最近聊天仍含答案。A3 若不优于 A2，应保留更简单的 A2，不能仅因多了演化模块宣称更有效。

### 8.3 测试情景

| 情景 | 期望与验证点 |
|---|---|
| 学习前后 | 同一类请求，教学后夜间主动先问，白天能够执行 |
| 措辞迁移 | 教学没出现过的表达，仍正确使用条件；不把规则原文放进测试请求 |
| 目标迁移 | 新坐标、新矿物、不同距离，不靠记住教学目标 |
| 行为迁移 | 教学说“采集”时可覆盖挖矿／砍树；只说“挖矿”时不能擅自扩展到砍树 |
| 偏好漂移 | 明确修改后及时采用新要求，同时保留无冲突的旧规则 |
| 临时与歧义 | “这次不用问”不永久修改；“以后别这样”关联不明时询问 |
| 干扰与冲突 | 无关闲聊、引用、假设、旧版技能不能改写当前规则 |
| 会话边界 | 重载、切换世界、过期确认、规则变化或昼夜变化后的旧确认均检查 |
| 真实执行 | 未同意时目标不变；同意后目标实际变化；缺工具不算成功 |

重放分两层：快照重放检查提取／选择，必须使用当时可见的信息；隔离游戏世界检查真实后果。单份快照不能验证长程寻路和后续任务完成，不能把一份静止诊断场景当成完整游玩测试。

### 8.4 数据分割与晋升门槛

- 开发集给候选生成器看错误，允许修改；晋升集的输入、标签与单例反馈不交给候选生成器。
- 每轮在开发集选出一个候选，再对其做一次独立晋升检查。失败后不能反复针对同一晋升集调参；需要补充经历、更新开发集，并使用预留的未使用样本。
- 最终审计集与前两者分离，用于报告比较，不参与候选选择。变体按场景家族分割，不能只是同一个案例换一句话后分别进入各集。
- 初始开发／晋升各 12 个场景，最终审计至少 24 个场景；这是工程试跑规模，不是统计充分性保证。报告各类别分母与重复运行情况。
- 最终审计记录固定配置下的多次运行；温度为零也不能直接假定完全可复现。不同教学顺序、至少两次独立世界会话需要覆盖。

预先约定的首轮工程门槛：

1. 所有关键禁令、旧确认失效与世界隔离场景，零误执行。
2. 晋升候选在偏好遵循与实际有效完成上不劣于当前版本，且在独立晋升集上至少改善一个预先定义的指标；不能只靠开发集改善、更频繁拒绝或询问达标。
3. 在当前有效的旧要求上不出现新的关键退化；偏好冲突按当前版本判定。
4. 确认单独统计：正确询问、无必要询问、漏问、歧义澄清；不能合并成一个“成功率”。
5. p50／p95 响应延迟、LLM 调用数、提示 token、资源占用有报告；功能改善与交互成本一起评估。

样本不足、收益不清楚或仅在开发集改善时不晋升。报告不以模型自己的“总结得分”作为唯一判据。

## 9. 本机计算预算

继续使用本地 4B、单请求槽。正常对话复用现有一次意图／偏好理解；规划仍一次只做一个动作，必要澄清才增加一次交互。不每帧调用，不为每句普通闲聊增加反思请求。

每次规划最多注入两条短技能和一条相关经历，初始为新增内容预留约 200 token 的硬预算，连同现有状态整体检查 2048 token 上下文上限。不能用字符数充当模型 token 数。状态装不下时先裁剪无关经历／软性说明，不能丢掉当前任务、关键条件和有效规则；仍装不下则缩小任务。

每轮最多生成两个受限候选，在开发集择优；只有一个候选进入独立晋升检查。相同快照比较多个版本时串行运行并记录总耗时。初期演化命令单独运行；不同时加载多个模型，不自动启动训练。

## 10. 实现与验收顺序

1. **可观察的基线**：先补经历 ID、mode、真实效果收据和各项指标，冻结 A0／A1 基线。没有可靠测量，先不加演化。
2. **条件化 PAHF**：昼夜规则、澄清恢复、反馈关联、即时修改；验证 A2 在迁移与偏好变化场景中的表现。
3. **最小 SkillEvo**：世界内候选、受限修改、开发／晋升分离、版本依赖、原子启用与回滚；比较 A3 与 A2。
4. **图形游玩检查**：在新建测试世界实测延迟、昼夜切换、停止与召回、真实采集；补齐跟随和碰撞的既有验证缺口。
5. **以后扩展**：明确标注的家园区域、完整作用范围检查、更丰富的合作技能；有可靠数据后再考虑 LoRA。

本阶段不把“有记忆”或“接上新论文方法”作为最终成果。交付应包含固定模型与配置、教学和反馈记录、各版本差异、独立测试结果、实际动作证据，以及失败和回滚的案例。
